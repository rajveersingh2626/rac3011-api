# Decisions (rac3011-api)

Ambiguities resolved during build step 0. Per spec §0 and §4.8 rule 8, the more restrictive option is chosen whenever the spec leaves room.

## RBAC / routes

- **`GET /clubs` list is scope-filtered**, not open to every authenticated user. §5.2's route table marks it `(auth)` with no explicit `[permission, s]` bracket, but §5.1 rule 2 states scope filtering applies to "every list route" by default, and §4.8 rule 8 says restrict when ambiguous. Implementation: `@RequirePermission('clubs:view')` at the controller, `ScopeService.clubFilter` applied in the service (empty scope → `{items: [], total: 0}`, never a full unscoped table).
- **`GET /zones` requires only `@Authenticated()`**, no permission gate — zones are non-sensitive reference data (four fixed names) and every seeded role that can reach any club-scoped screen needs them for a picker.
- **`GET /permissions` requires `roles:manage`.** The route table doesn't bracket it, but it's only useful alongside role management, and permission descriptions can hint at internal structure — kept behind the same gate as `/roles`.
- **`DELETE /files/:id` returns 403 for out-of-scope callers**, not 404. Ground rule 4 (404 for reads) is about preventing enumeration of *existing rows via reads*; delete is a mutating action, and the rest of the matrix (e.g. `PATCH /clubs/A/facts`) uses 403 for out-of-scope mutations. `GET /files/:id` on a private-tier file still 404s per the rule.

## Auth

- **Better Auth's own routes stay at `/auth/*`; the custom second-factor and trusted-device routes moved to `/second-factor/*` and `/trusted-devices/*`** (not `/auth/second-factor/*` / `/auth/trusted-devices/*` as literally written in §4.1/§5.2). `@thallesp/nestjs-better-auth` mounts middleware that claims the *entire* `basePath` prefix unconditionally (`matchesBasePath` is a plain prefix match, not a route table) and returns 404 for any sub-path it doesn't itself define — a Nest controller mounted under `/auth/second-factor` is unreachable. Moving Better Auth's own `basePath` instead was considered and rejected: it risks touching cookie/CSRF/trustedOrigins path assumptions that are harder to get right than moving two bespoke routes that no external tooling depends on.
- **The second factor is implemented as our own `mfaPending` session column + gate, not Better Auth's built-in `twoFactor` pending-cookie flow.** Better Auth's own sign-in-time 2FA short-circuit issues a separate short-lived cookie before a full session exists; our design instead always creates a full session at password sign-in (`session.additionalFields.mfaPending` defaults `true`) and blocks every route except `@SecondFactorStage()` ones (`/second-factor/verify`, `/second-factor/resend`) until it's cleared. This matches the `SessionContextPort`/`PermissionGuard` shape already committed in the prior session (`ResolvedSession.mfaPending`) and keeps one auth code path instead of two. `POST /second-factor/verify {method:'email'}` calls Better Auth's `auth.api.checkVerificationOTP` (stateless, identifier-based, no coupling to their pending-cookie machinery); `{method:'totp'}` calls `auth.api.verifyTOTP`, which the installed SDK version supports running against a normal established session, not only its own pending state.
- **Trusted-device skip is resolved lazily inside `SessionContextAdapter.fromRequest`**, not via a Better Auth `AfterHook` on `/sign-in/email`. Wiring into their sign-in lifecycle to flip `mfaPending` at creation time was considered, but the exact `AfterHook` context shape (what's available synchronously vs. only via a follow-up query) couldn't be verified against live docs. Instead, every request resolution checks: if `mfaPending` and a valid `trusted_device` cookie hash exists for the user, flip `mfaPending` false and persist it. Functionally equivalent (the very next authenticated call after sign-in clears it), fully within code this repo owns end-to-end, and it's what's covered by `test/auth.e2e.ts`.
- **`scripts/migrate-legacy-users.ts` does not migrate legacy TOTP secrets into Better Auth's `two_factor` table.** Better Auth encrypts `TwoFactor.secret` at rest with a key derived internally from `AUTH_SECRET` (`ctx.context.secretConfig`, not exposed as a public API); writing the legacy plaintext/whatever-format secret directly into that column would either fail verification silently or (worse) appear to work while being unverifiable, and there's no way to confirm the right derivation without running against a live instance. Migrated users whose legacy account had TOTP enabled land with `user.twoFactorEnabled = false` and re-enroll via the normal TOTP setup flow, which generates and encrypts the secret correctly. Their email-OTP second factor still works immediately post-migration.
- **Legacy password hash compatibility only rejects unknown (`$2`-less) hashes; it does not yet send the "reset your password" notification described in §4.2.** Better Auth's `emailAndPassword.password.verify` callback receives only `{hash, password}`, not the user/email, so there's no clean place to trigger a templated email from inside it. The reset-required email is deferred to the legacy user migration script (`scripts/migrate-legacy-users.ts`), which does have the user record and can flag `TwoFactor`/mark accounts needing a reset up front, or to a dedicated `/auth/sign-in` failure hook once one is verified against a running instance.
- **Test-only cookie relaxation**: `secure` is `env.NODE_ENV === 'production'` (spec literally says "except when NODE_ENV=development") and `domain` is omitted when `NODE_ENV === 'test'`. E2e tests run supertest against an in-memory HTTP server (`http://127.0.0.1:<port>`, not TLS, not host `localhost`); a `Secure`-flagged or `Domain=localhost`-scoped cookie is never replayed by a spec-compliant cookie jar, which silently 401s every request after sign-in. This only changes behaviour for `NODE_ENV=test`; dev and prod cookie behaviour match the spec exactly.
- **Second-factor resend rate limiting (3/10min per email) is in-memory, not Redis-backed.** Correct behind a single instance (matches this repo's current one-process API deployment); flagged here so it's replaced with a shared store before running more than one API replica.

## Storage (§3A)

- **`POST /files/grants` and `PATCH /files/grants/:grantId` require only `@Authenticated()`; the owning permission and scope are checked inside `StorageService`,** because the required permission varies per `resourceType` in the request body and can't be expressed as a single static `@RequirePermission` decorator.
- **`GET /files/:id` also requires `@Authenticated()`** (a session), even though public-tier files 301-redirect to a public CDN URL. The route table doesn't say whether the public-tier branch needs a session; restricting by default rather than exposing an anonymous file-metadata lookup endpoint.
- **`UploadThingAdapter` cannot presign uploads with the installed `uploadthing` server SDK** (`UTApi` has no client-presign API in this version — that flow is normally handled by mounting `createUploadthing`'s own route handler, which doesn't fit the uniform grant/finalise `StoragePort` interface). The adapter instead assumes the client uploads via UploadThing's hosted client SDK directly against the tier's token, and `PATCH /files/grants/:grantId {providerKey}` resolves that reported key to a CDN URL via `getFileUrls`. Verified against the SDK's exported types only; not exercised against a live UploadThing app (`STORAGE_DRIVER=stub` is the tested path; `live` needs verification on the VPS per §3A's own note about this network blocking `*.r2.cloudflarestorage.com`).
- **`StoredFile.id` encodes what each live adapter needs to resolve `delete(fileId)` without touching Prisma from an adapter** (`*.repository.ts` is the only place allowed to import `@prisma/client`, and `delete` only receives the id, not the tier). `UploadThingAdapter` uses `"<tier>:<key>"`; `R2Adapter` uses the bare R2 object key (single bucket, no ambiguity). `StubStorageAdapter` just needs *an* id and uses the provider key directly.

## Deployment

- **`prisma` (the CLI) moved from `devDependencies` to `dependencies`.** `docker-entrypoint.sh` runs `npx prisma migrate deploy` before starting the server, but the runtime Docker stage installs with `npm ci --omit=dev`; without this move the container would either fail offline or silently fetch the CLI from the network on every start.
- **`Dockerfile` copies `prisma/schema` (directory) and `prisma.config.ts`, not `prisma/schema.prisma`.** The schema was split into `prisma/schema/*.prisma` files before this session; the single-file `COPY` target hasn't existed since, so the image build was broken. Fixed to match `prisma.config.ts`'s `schema: 'prisma/schema'`.
- **`start:prod`/`start:worker` run `node dist/src/main`, not `node dist/main`** (as spec §1.1 literally lists). `nest build` compiles two top-level source roots (`src/` and `prisma/`) and preserves each one's path under `dist/`, so the entry point is `dist/src/main.js`; verified against the actual `npm run build` output, not assumed.

## Test infrastructure

- **`resetTestDatabase()` (destructive `TRUNCATE` + reseed) is called once from `test/global-setup.ts`, not from each e2e file's `beforeAll`.** Empirically, `vitest.config.ts`'s `fileParallelism: false` (nested inside the `e2e` project's `test` block) did not prevent two e2e files' `beforeAll` hooks from interleaving in-process against the one shared Postgres testcontainer — confirmed by reproducing a `TRUNCATE` from one file wiping a club row another file had just inserted. System data (roles/permissions/zones/points/settings/content) is seeded once, globally; each e2e file creates its own additively-named fixtures (clubs/users prefixed per file, e.g. `AU-CLUB-A`, `MX-CLUB-A`) so concurrent files never collide on unique keys. `resetTestDatabase()` and the advisory-lock guard around it are kept in `test/db.ts` for any future test that legitimately needs a full wipe.
- **A handful of Nest providers needed explicit `@Inject(Token)` instead of implicit constructor-type inference** (`EmailProviderPool`'s `EmailUsageRepository`/`ClockPort` params, `RbacRouteAudit`'s `ModulesContainer`/`Reflector` params) — under `unplugin-swc` (used by vitest) these resolved to `undefined` at runtime despite compiling and type-checking cleanly, while the exact same code booted fine under `tsx`. Root cause not fully isolated (suspected `emitDecoratorMetadata` interaction with swc's output for certain import shapes); the fix is mechanical and low-risk. If a provider throws `Nest can't resolve dependencies of X (?, ...)` for a class that's clearly registered, try adding an explicit `@Inject()` before assuming a real DI misconfiguration.
- **`RbacRouteAudit.findUndecoratedRoutes` guards `module.controllers?.values() ?? []`.** At least one module in the graph (observed with `@thallesp/nestjs-better-auth`'s dynamically registered module) produced a `Module` instance where `.controllers` was `undefined` rather than an empty `Map`, crashing the boot-time audit before it could report anything.
- **`RbacModule` imports `AuthModule`** so `PermissionGuard` can resolve `SessionContextPort` (provided and exported by `AuthModule`). Both modules are otherwise independent; `AuthModule` does not import `RbacModule`, so there's no cycle.

## Reporting (§3.6, §4.8, §5.2, §6.8)

- **`@RequirePermission` now accepts multiple keys (`@RequirePermission('a', 'b')` = "a OR b"), not just one.** Several routes in §5.2's table are gated by an explicit disjunction ("reports:submit own / reports:review s" for `GET/POST /reports`, "requests:manage; GET also reports:submit for open ones" for report requests). The existing decorator/guard only supported a single permission key. Extended `RequirePermission` to a rest-param array (backward compatible: existing single-arg call sites are unaffected) and `PermissionGuard` to pass if *any* listed permission is granted. Added `ScopeService.clubFilterAny`/`assertCanAccessClubAny` (union of `clubFilter`/`assertCanAccessClub` across the listed permissions) so services can compute the right scope regardless of which permission the caller actually holds.
- **`GET /reports` (and `GET /reports/:id`, `GET /report-schemas`) return 403, not 200-empty, for a caller holding neither `reports:submit` nor `reports:review`** (e.g. plain `member`, `project_admin`, `editing_team`). §4.8's own denial-matrix template row lists `member`/`project_admin` as "empty" and `editing_team` as `403` for the same missing-permission situation, which is internally inconsistent for a resource with no admitted broader read grant. Per §4.8 rule 8 ("when in doubt, restrict"), chose permission-gate-first (guard 403) uniformly over exposing a scope-only-filtered list to any authenticated user. `test/rbac/matrix.e2e.ts`'s reports section documents this explicitly.
- **`values.notes` (the schema's "Notes" section field, fieldKey `notes`) is excluded from `validateReportValues`/`collectClubIdsInValues` and is never read from or written to the `values` JSON blob.** `Report.notes` is already a first-class column (used by `PATCH /reports/:id {notes}` per the route table), and the web spec's "Notes for the district" textarea is one control, not two. The schema still seeds a `notes` field (per §6.8's literal field list, so the Form Builder can show/reorder/relabel it), but it's cosmetic metadata only — the validator special-cases and skips it by `fieldKey`.
- **`PATCH /reports/:id {status:'submitted'}` only accepts the transition from `draft` (or `queried`, so an officer can resubmit before a ZRR replies-in-reverse — not exercised in practice since the query-reply route already does the `queried -> submitted` transition explicitly). `values`/`notes` edits are only allowed while `status` is `draft` or `queried`** — restrictive reading of "submitting a report is `PATCH /reports/:id {status:'submitted'}`" (§5.1.1): once `submitted` or `scored`, the report is immutable via this route (a fresh query is the only way back to an editable state).
- **`ScopeService.clubFilter`/`ReportsRepository.whereFor` never merge the caller-supplied `filter[clubId]` with the scope directly — the service narrows scope first via `ScopeService.narrowClubs`, then the repository builds `WHERE clubId IN (narrowed scope)`, dropping the raw filter.** An earlier draft `OR`'d the scope where-clause with a raw `clubId: filter.clubId` fallback, which would have let any caller widen their own list query to an arbitrary club id by passing `filter[clubId]` — the exact scope-leak-through-filters problem §4.8 rule 3 warns about. Caught in review before it shipped; no scope-leak test failed because none existed yet, so `test/reports.e2e.ts`'s "ZRR sees only their zone" case is the regression guard for this specifically.
- **`ReportRequest.audience` is `{all?: boolean; clubIds?: string[]; zoneIds?: string[]}`**, not fully specified by the spec. A club is in-audience if `all`, or its id is in `clubIds`, or its `zoneId` is in `zoneIds`. `GET /report-requests` for a `reports:submit`-only caller returns every request whose audience currently matches their club (not filtered further by "already responded" — "open" is read as "applicable to me", the simpler and more restrictive of the two plausible readings, since narrowing further risks hiding a request the club still needs to act on).
- **The points engine (spec step 5) is explicitly out of scope here.** `src/points/adapters/point-source.port.ts` is a bare `PointSourceAdapter` interface stub with no implementation or module wiring — nothing in `src/reports/` or `src/points/` computes or persists `club_point_entries`. `src/points/adapters/report-field.derive.ts` implements and unit-tests the exact §6.8 derivation rules (`camps_organised`, `projects_initiated`, `vocational_workshops`, `flagship_continued`, `international_activities`, `max_collaborators`, plus the direct club-field and `filed_on_time` sources) as pure functions over a report's `values`/`filedOnTime`, ready for step 5 to call once it exists — but nothing currently calls `deriveReportPointSources` in the request path.
- **`AssistPort` mirrors `StoragePort`'s live/stub adapter-switch pattern exactly**: new env var `ASSIST_DRIVER` (`live|stub`, default `stub`, mirroring `STORAGE_DRIVER`), `AnthropicAssistAdapter` built against the real `@anthropic-ai/sdk` (already a dependency) using `env.ANTHROPIC_MODEL`/`env.ANTHROPIC_API_KEY`, `StubAssistAdapter` for tests/unconfigured envs. `GET /reports/:id/assist` is `reports:score`-gated per the route table; not exercised against a live Anthropic key in tests (`ASSIST_DRIVER` defaults to `stub`, matching the storage module's own untested-live-path precedent).
- **`report.submitted`/`report.queried` are plain in-process `@nestjs/event-emitter` events** (`EventEmitterModule.forRoot()` added to `AppModule`, first use of it in this codebase), payload shapes exported from `src/reports/report.events.ts`. Nothing subscribes yet — step 5 (points recompute) and step 9 (notifications/audit fan-out beyond what §4.6 already mandates inline) are the intended subscribers. Kept deliberately dependency-free (no queue, no BullMQ) since nothing consumes them yet and adding a queue for zero consumers would be unverifiable speculation.

## Caching and performance (§14)

- **`PrismaService`'s constructor returns `this.$extends(cacheInvalidationExtension)` cast back to `PrismaService`**, not `this`. Prisma's `$extends()` always returns a new proxied client rather than mutating the receiver, and every `*.repository.ts` in this repo already injects the concrete `PrismaService` class as its constructor param type, so changing that type across ~30 files was rejected as unnecessarily invasive. `onModuleInit`/`onModuleDestroy` (and a bespoke `onQuery` passthrough used only by test query-count assertions) are reattached onto the extended proxy via `Object.assign` in the constructor, since Nest calls lifecycle hooks by duck-typing (`typeof instance.onModuleInit === 'function'`), not `instanceof`. `class PrismaService extends PrismaClient<{log:[{emit:'event',level:'query'}]}>` (an explicit generic, not the bare `extends PrismaClient`) is required for `$on('query', ...)`/`onQuery` to type-check at all — Prisma's `$on` overload resolves its allowed event-name union from the class's own generic `log` config, which defaults to `never` when the subclass doesn't parameterise it.
- **The Prisma cache-invalidation extension (`src/prisma/cache-invalidation.extension.ts`) maps model → tags via `MODEL_TAG_MAP` (`src/cache/model-tag-map.ts`) and enqueues one purge per write**, covering `create|createMany|update|updateMany|upsert|delete|deleteMany` on every model through a single `$allOperations` hook (not one hook per model) so a newly added model needs no extension change, only a `MODEL_TAG_MAP` entry (enforced by `model-tag-map.spec.ts`'s exhaustiveness test, which statically scans a maintained list of public-facing `*.repository.ts` files for `this.prisma.<model>.` calls — this list must be kept in sync when a new public repository is added; `ProjectClub` is added by hand since it's read only via a nested Prisma `select`/relation, not a direct delegate call the regex can see).
- **`TAG_URL_MAP` (`src/cache/tag-url-map.ts`) lists only parameter-free public URLs** (`/public/clubs`, `/public/projects`, etc.), not slug-based detail routes (`/public/clubs/:slug`, `/public/projects/:slug`, `/public/events/:slug`, `/public/content/:pageKey`). Cloudflare purge-by-URL needs exact URLs and there is no bounded, enumerable set of slugs to purge ahead of time. L2 (Redis) invalidation for these detail routes is still fully correct and immediate — every distinct slug's cache key is a member of the same tag set as the list route, so `delByTag` deletes all of them — only the **edge** cache for a specific detail page can lag, bounded by `s-maxage` (600s), matching §14.4.3's own "never permanent" fallback language. The one exception is `/public/projects-summary/:key`, whose 5 keys are a small fixed enum (`PROJECT_KEYS`) and are enumerated concretely.
- **`CacheModule` registers `CachePurgeProcessor` (the BullMQ `cache.purge` worker) in both the API and worker processes**, not worker-only like the pre-existing `LinkHealthModule` pattern. Cache-invalidating writes happen inside API request handlers, so the API process is the natural place to also drain its own purge queue instead of depending on the worker always being reachable; both being able to consume is strictly more available, at the cost of needing `CLOUDFLARE_*` env vars on both Dokploy apps.
- **`NoopCloudflarePurgeClient` (bound whenever `CLOUDFLARE_API_EMAIL`/`_API_KEY`/`_ZONE_ID` are unset) records every call it skips** (`purgedUrlBatches`, `purgedPrefixes`), not just logs it. This doubles as the "fake Cloudflare client" the §14.7.2 e2e test needs to assert purge correctness — no separate test-only provider wiring was added, since local/test envs never set the Cloudflare vars and therefore always resolve to this class already.
- **`GET /public/live` (visitor count) and the ICS feeds (`/public/events/:slug.ics`, `/public/calendar.ics`) are deliberately excluded from `@CacheTags`/L2 caching.** `/public/live` exists specifically to stay live (5s edge TTL, polled every 10s by the frontend); putting it behind the 3600s L2 TTL would defeat its purpose. The ICS routes return `text/calendar`, not JSON, and the interceptor's L2 store round-trips values through `JSON.stringify`/`JSON.parse` — fine for a string body, but combined with Nest's `@Header('Content-Type', ...)` decorator ordering relative to interceptor short-circuiting, this was not verified and was judged not worth the risk for two low-traffic feed endpoints; they keep their pre-existing manual `setPublicCache(res, 300)` calls untouched.
- **Env additions (`CLOUDFLARE_API_EMAIL`, `CLOUDFLARE_API_KEY`, `CLOUDFLARE_ZONE_ID`, `CACHE_INVALIDATION`) are all optional/defaulted in `src/config/env.ts`**, not added to the production-required check in `parseEnv`. Omitting them degrades gracefully (edge purge skipped, logged) rather than blocking boot — matching `STORAGE_DRIVER=stub`'s existing precedent, and appropriate since Cloudflare purge is an optimisation, not a correctness requirement (L2/Postgres are still always correct).
- **`purgeAllStandalone()` (`src/cache/purge-all.standalone.ts`) is called from both `prisma/seed.ts` and `prisma/seed-system.ts`'s CLI entrypoint**, using its own short-lived, low-retry IORedis connection (`connectTimeout: 3000`, `maxRetriesPerRequest: 1`) rather than the app's long-lived `createCacheRedis()` config, and swallows all errors. `docker-entrypoint.sh` runs `seed-system.js` before the server starts with `set -e`; a Redis outage at deploy time must never block the container from booting, so this path can never throw.

## Site rebuild trigger (spec §14.9 follow-up)

- **`SITE_REBUILD_TAGS` excludes `zones` in addition to the spec's explicit `reports`/`points`/`members` list.** `Zone` only backs `GET /zones` (`@Authenticated()`-only, per the RBAC decision above) and the one place a public response mentions zone counts (`PublicHomeService`'s `home.stats`) reads a stored `Setting` value, not a live `Zone` query - so a `Zone` write never changes any `/public/*` payload. Per rule 8 (restrict when ambiguous), a tag with no public-facing effect stays off the rebuild allow-list; `site-rebuild-tags.spec.ts`'s exhaustiveness test enforces that every `CacheTag` is accounted for as either allow-listed or excluded, so a newly added tag can't silently land in neither.
- **The rebuild hook lives inside `CacheInvalidator.purge(tags)`** (calls `SiteRebuildTrigger.maybeEnqueue(tags)` after the existing L2/edge purge enqueue), not inside the Prisma extension itself or scattered across callers. `purge()` already gates on `CACHE_INVALIDATION=off` and is the one function every write-through-Prisma path reaches unconditionally (§14.4); `purgeAll()` (the seed/migration full-purge path) is deliberately left untouched, since seed runs already bypass `CacheInvalidator` entirely via `purgeAllStandalone()`'s own short-lived Redis connection.
- **Debounce is the fixed-`jobId` + `delay` BullMQ pattern**, not a Redis key with a TTL or a cron sweep: `addDelayedJob-6.lua` returns the existing job (via `handleDuplicatedJob`) when a job with that id already exists rather than erroring or resetting its delay, so repeated `queue.add()` calls during the window are no-ops and the job created by the first write in a burst is the only one that ever runs. `removeOnComplete: true` clears the key afterward so the next write starts a fresh window.
- **`GithubDispatchClient` and `SiteRebuildTrigger` each independently check `SITE_REBUILD_ENABLED`/token presence** rather than trusting the caller. This is deliberate belt-and-braces: a job already sitting in the delayed queue when `SITE_REBUILD_ENABLED` flips to `off` (or the token is pulled) must still no-op cleanly when it eventually runs, not throw.
