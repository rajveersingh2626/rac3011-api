# Decisions (rac3011-api)

Ambiguities resolved during build step 0. Per spec §0 and §4.8 rule 8, the more restrictive option is chosen whenever the spec leaves room.

## RBAC / routes

- **`GET /clubs` list is scope-filtered**, not open to every authenticated user. §5.2's route table marks it `(auth)` with no explicit `[permission, s]` bracket, but §5.1 rule 2 states scope filtering applies to "every list route" by default, and §4.8 rule 8 says restrict when ambiguous. Implementation: `@RequirePermission('clubs:view')` at the controller, `ScopeService.clubFilter` applied in the service (empty scope → `{items: [], total: 0}`, never a full unscoped table).
- **`GET /zones` requires only `@Authenticated()`**, no permission gate — zones are non-sensitive reference data (four fixed names) and every seeded role that can reach any club-scoped screen needs them for a picker.
- **`GET /permissions` requires `roles:manage`.** The route table doesn't bracket it, but it's only useful alongside role management, and permission descriptions can hint at internal structure — kept behind the same gate as `/roles`.
- **`DELETE /files/:id` returns 403 for out-of-scope callers**, not 404. Ground rule 4 (404 for reads) is about preventing enumeration of *existing rows via reads*; delete is a mutating action, and the rest of the matrix (e.g. `PATCH /clubs/A/facts`) uses 403 for out-of-scope mutations. `GET /files/:id` on a private-tier file still 404s per the rule.

## Auth

- **Better Auth's own routes stay at `/auth/*`; the custom second-factor and trusted-device routes moved to `/second-factor/*` and `/trusted-devices/*`** (not `/auth/second-factor/*` / `/auth/trusted-devices/*` as literally written in §4.1/§5.2). `@thallesp/nestjs-better-auth` mounts middleware that claims the *entire* `basePath` prefix unconditionally (`matchesBasePath` is a plain prefix match, not a route table) and returns 404 for any sub-path it doesn't itself define — a Nest controller mounted under `/auth/second-factor` is unreachable. Moving Better Auth's own `basePath` instead was considered and rejected: it risks touching cookie/CSRF/trustedOrigins path assumptions that are harder to get right than moving two bespoke routes that no external tooling depends on.
- **The second factor is implemented as our own `mfaPending` session column + gate, not Better Auth's built-in `twoFactor` pending-cookie flow.** Better Auth's own sign-in-time 2FA short-circuit issues a separate short-lived cookie before a full session exists; our design instead always creates a full session at password sign-in (`session.additionalFields.mfaPending` defaults `true`) and blocks every route except `@SecondFactorStage()` ones (`/second-factor/verify`, `/second-factor/resend`) until it's cleared. This matches the `SessionContextPort`/`PermissionGuard` shape already committed in the prior session (`ResolvedSession.mfaPending`) and keeps one auth code path instead of two. `POST /second-factor/verify {method:'email'}` calls Better Auth's `auth.api.checkVerificationOTP` (stateless, identifier-based, no coupling to their pending-cookie machinery); `{method:'totp'}` calls `auth.api.verifyTOTP`, which the installed SDK version supports running against a normal established session, not only its own pending state.
- **Trusted-device skip is resolved lazily inside `SessionContextAdapter.fromRequest`**, not via a Better Auth `AfterHook` on `/sign-in/email`. Wiring into their sign-in lifecycle to flip `mfaPending` at creation time was considered, but the exact `AfterHook` context shape (what's available synchronously vs. only via a follow-up query) couldn't be verified against live docs. Instead, every request resolution checks: if `mfaPending` and a valid `trusted_device` cookie hash exists for the user, flip `mfaPending` false and persist it. Functionally equivalent (the very next authenticated call after sign-in clears it), fully within code this repo owns end-to-end, and it's what's covered by `test/auth.e2e.ts`.
- **Legacy password hash compatibility only rejects unknown (`$2`-less) hashes; it does not yet send the "reset your password" notification described in §4.2.** Better Auth's `emailAndPassword.password.verify` callback receives only `{hash, password}`, not the user/email, so there's no clean place to trigger a templated email from inside it. The reset-required email is deferred to the legacy user migration script (`scripts/migrate-legacy-users.ts`), which does have the user record and can flag `TwoFactor`/mark accounts needing a reset up front, or to a dedicated `/auth/sign-in` failure hook once one is verified against a running instance.
- **Test-only cookie relaxation**: `secure` is `env.NODE_ENV === 'production'` (spec literally says "except when NODE_ENV=development") and `domain` is omitted when `NODE_ENV === 'test'`. E2e tests run supertest against an in-memory HTTP server (`http://127.0.0.1:<port>`, not TLS, not host `localhost`); a `Secure`-flagged or `Domain=localhost`-scoped cookie is never replayed by a spec-compliant cookie jar, which silently 401s every request after sign-in. This only changes behaviour for `NODE_ENV=test`; dev and prod cookie behaviour match the spec exactly.
- **Second-factor resend rate limiting (3/10min per email) is in-memory, not Redis-backed.** Correct behind a single instance (matches this repo's current one-process API deployment); flagged here so it's replaced with a shared store before running more than one API replica.

## Storage (§3A)

- **`POST /files/grants` and `PATCH /files/grants/:grantId` require only `@Authenticated()`; the owning permission and scope are checked inside `StorageService`,** because the required permission varies per `resourceType` in the request body and can't be expressed as a single static `@RequirePermission` decorator.
- **`GET /files/:id` also requires `@Authenticated()`** (a session), even though public-tier files 301-redirect to a public CDN URL. The route table doesn't say whether the public-tier branch needs a session; restricting by default rather than exposing an anonymous file-metadata lookup endpoint.
- **`UploadThingAdapter` cannot presign uploads with the installed `uploadthing` server SDK** (`UTApi` has no client-presign API in this version — that flow is normally handled by mounting `createUploadthing`'s own route handler, which doesn't fit the uniform grant/finalise `StoragePort` interface). The adapter instead assumes the client uploads via UploadThing's hosted client SDK directly against the tier's token, and `PATCH /files/grants/:grantId {providerKey}` resolves that reported key to a CDN URL via `getFileUrls`. Verified against the SDK's exported types only; not exercised against a live UploadThing app (`STORAGE_DRIVER=stub` is the tested path; `live` needs verification on the VPS per §3A's own note about this network blocking `*.r2.cloudflarestorage.com`).
- **`StoredFile.id` encodes what each live adapter needs to resolve `delete(fileId)` without touching Prisma from an adapter** (`*.repository.ts` is the only place allowed to import `@prisma/client`, and `delete` only receives the id, not the tier). `UploadThingAdapter` uses `"<tier>:<key>"`; `R2Adapter` uses the bare R2 object key (single bucket, no ambiguity). `StubStorageAdapter` just needs *an* id and uses the provider key directly.

## Test infrastructure

- **`resetTestDatabase()` (destructive `TRUNCATE` + reseed) is called once from `test/global-setup.ts`, not from each e2e file's `beforeAll`.** Empirically, `vitest.config.ts`'s `fileParallelism: false` (nested inside the `e2e` project's `test` block) did not prevent two e2e files' `beforeAll` hooks from interleaving in-process against the one shared Postgres testcontainer — confirmed by reproducing a `TRUNCATE` from one file wiping a club row another file had just inserted. System data (roles/permissions/zones/points/settings/content) is seeded once, globally; each e2e file creates its own additively-named fixtures (clubs/users prefixed per file, e.g. `AU-CLUB-A`, `MX-CLUB-A`) so concurrent files never collide on unique keys. `resetTestDatabase()` and the advisory-lock guard around it are kept in `test/db.ts` for any future test that legitimately needs a full wipe.
- **A handful of Nest providers needed explicit `@Inject(Token)` instead of implicit constructor-type inference** (`EmailProviderPool`'s `EmailUsageRepository`/`ClockPort` params, `RbacRouteAudit`'s `ModulesContainer`/`Reflector` params) — under `unplugin-swc` (used by vitest) these resolved to `undefined` at runtime despite compiling and type-checking cleanly, while the exact same code booted fine under `tsx`. Root cause not fully isolated (suspected `emitDecoratorMetadata` interaction with swc's output for certain import shapes); the fix is mechanical and low-risk. If a provider throws `Nest can't resolve dependencies of X (?, ...)` for a class that's clearly registered, try adding an explicit `@Inject()` before assuming a real DI misconfiguration.
- **`RbacRouteAudit.findUndecoratedRoutes` guards `module.controllers?.values() ?? []`.** At least one module in the graph (observed with `@thallesp/nestjs-better-auth`'s dynamically registered module) produced a `Module` instance where `.controllers` was `undefined` rather than an empty `Map`, crashing the boot-time audit before it could report anything.
- **`RbacModule` imports `AuthModule`** so `PermissionGuard` can resolve `SessionContextPort` (provided and exported by `AuthModule`). Both modules are otherwise independent; `AuthModule` does not import `RbacModule`, so there's no cycle.
