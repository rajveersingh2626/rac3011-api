# Decisions (rac3011-api)

Ambiguities resolved during build step 0. Per spec §0 and §4.8 rule 8, the more restrictive option is chosen whenever the spec leaves room.

## RBAC / routes

- **`GET /clubs` list is scope-filtered**, not open to every authenticated user. §5.2's route table marks it `(auth)` with no explicit `[permission, s]` bracket, but §5.1 rule 2 states scope filtering applies to "every list route" by default, and §4.8 rule 8 says restrict when ambiguous. Implementation: `@RequirePermission('clubs:view')` at the controller, `ScopeService.clubFilter` applied in the service (empty scope → `{items: [], total: 0}`, never a full unscoped table).
- **`GET /zones` requires only `@Authenticated()`**, no permission gate — zones are non-sensitive reference data (four fixed names) and every seeded role that can reach any club-scoped screen needs them for a picker.
- **`GET /permissions` requires `roles:manage`.** The route table doesn't bracket it, but it's only useful alongside role management, and permission descriptions can hint at internal structure — kept behind the same gate as `/roles`.
- **`DELETE /files/:id` returns 403 for out-of-scope callers**, not 404. Ground rule 4 (404 for reads) is about preventing enumeration of *existing rows via reads*; delete is a mutating action, and the rest of the matrix (e.g. `PATCH /clubs/A/facts`) uses 403 for out-of-scope mutations. `GET /files/:id` on a private-tier file still 404s per the rule.

## Auth

- **Better Auth's own routes stay at `/auth/*`; the custom second-factor and trusted-device routes moved to `/second-factor/*` and `/trusted-devices/*`** (not `/auth/second-factor/*` / `/auth/trusted-devices/*` as literally written in §4.1/§5.2). `@thallesp/nestjs-better-auth` mounts middleware that claims the *entire* `basePath` prefix unconditionally (`matchesBasePath` is a plain prefix match, not a route table) and returns 404 for any sub-path it doesn't itself define — a Nest controller mounted under `/auth/second-factor` is unreachable. Moving Better Auth's own `basePath` instead was considered and rejected: it risks touching cookie/CSRF/trustedOrigins path assumptions that are harder to get right than moving two bespoke routes that no external tooling depends on.
- **The second factor is implemented as our own `mfaPending` session column + gate, not Better Auth's built-in `twoFactor` pending-cookie flow.** Better Auth's own sign-in-time 2FA short-circuit issues a separate short-lived cookie before a full session exists; our design instead always creates a full session at password sign-in (`session.additionalFields.mfaPending` defaults `true`) and blocks every route except `@SecondFactorStage()` ones (`/second-factor/verify`, `/second-factor/resend`) until it's cleared. This matches the `SessionContextPort`/`PermissionGuard` shape already committed in the prior session (`ResolvedSession.mfaPending`) and keeps one auth code path instead of two. `POST /second-factor/verify {method:'email'}` calls Better Auth's `auth.api.checkVerificationOTP` (stateless, identifier-based, no coupling to their pending-cookie machinery); `{method:'totp'}` calls `auth.api.verifyTOTP`, which the installed SDK version supports running against a normal established session, not only its own pending state.
- **Trusted-device skip is resolved lazily inside `SessionContextAdapter.fromRequest`**, not via a Better Auth `AfterHook` on `/sign-in/email`. Wiring into their sign-in lifecycle to flip `mfaPending` at creation time was considered, but the exact `AfterHook` context shape (what's available synchronously vs. only via a follow-up query) couldn't be verified against live docs. Instead, every request resolution checks: if `mfaPending` and a valid `trusted_device` cookie hash exists for the user, flip `mfaPending` false and persist it. Functionally equivalent (the very next authenticated call after sign-in clears it), fully within code this repo owns end-to-end, and it's what's covered by `test/auth.e2e.ts`.
- **`scripts/migrate-legacy-users.ts` does not migrate legacy TOTP secrets into Better Auth's `two_factor` table.** Better Auth encrypts `TwoFactor.secret` at rest with a key derived internally from `AUTH_SECRET` (`ctx.context.secretConfig`, not exposed as a public API); writing the legacy plaintext/whatever-format secret directly into that column would either fail verification silently or (worse) appear to work while being unverifiable, and there's no way to confirm the right derivation without running against a live instance. Migrated users whose legacy account had TOTP enabled land with `user.twoFactorEnabled = false` and re-enroll via the normal TOTP setup flow, which generates and encrypts the secret correctly. Their email-OTP second factor still works immediately post-migration.
- **Legacy password hash compatibility only rejects unknown (`$2`-less) hashes; it does not yet send the "reset your password" notification described in §4.2.** Better Auth's `emailAndPassword.password.verify` callback receives only `{hash, password}`, not the user/email, so there's no clean place to trigger a templated email from inside it. The reset-required email is deferred to the legacy user migration script (`scripts/migrate-legacy-users.ts`), which does have the user record and can flag `TwoFactor`/mark accounts needing a reset up front, or to a dedicated `/auth/sign-in` failure hook once one is verified against a running instance.
- **Test-only cookie relaxation**: `secure` is `env.NODE_ENV === 'production'` (spec literally says "except when NODE_ENV=development") and `domain` is omitted when `NODE_ENV === 'test'`. E2e tests run supertest against an in-memory HTTP server (`http://127.0.0.1:<port>`, not TLS, not host `localhost`); a `Secure`-flagged or `Domain=localhost`-scoped cookie is never replayed by a spec-compliant cookie jar, which silently 401s every request after sign-in. This only changes behaviour for `NODE_ENV=test`; dev and prod cookie behaviour match the spec exactly.
- **Second-factor resend rate limiting (3/10min per email) is in-memory, not Redis-backed.** Correct behind a single instance (matches this repo's current one-process API deployment); flagged here so it's replaced with a shared store before running more than one API replica.

## Storage (§3A)

- **`POST /files/grants` and `PATCH /files/grants/:grantId` require only `@Authenticated()`; the owning permission and scope are checked inside `StorageService`,** because the required permission varies per `resourceType` in the request body and can't be expressed as a single static `@RequirePermission` decorator.
- **`GET /files/:id` also requires `@Authenticated()`** (a session), even though public-tier files 301-redirect to a public CDN URL. The route table doesn't say whether the public-tier branch needs a session; restricting by default rather than exposing an anonymous file-metadata lookup endpoint.
- **`UploadThingAdapter` cannot presign uploads with the installed `uploadthing` server SDK** (`UTApi` has no client-presign API in this version — that flow is normally handled by mounting `createUploadthing`'s own route handler, which doesn't fit the uniform grant/finalise `StoragePort` interface). The adapter instead assumes the client uploads via UploadThing's hosted client SDK directly against the tier's token, and `PATCH /files/grants/:grantId {providerKey}` resolves that reported key to a CDN URL via `getFileUrls`. Verified against the SDK's exported types only; not exercised against a live UploadThing app (`STORAGE_DRIVER=stub` is the tested path; `live` needs verification on the VPS per §3A's own note about this network blocking `*.r2.cloudflarestorage.com`).
- **`StoredFile.id` encodes what each live adapter needs to resolve `delete(fileId)` without touching Prisma from an adapter** (`*.repository.ts` is the only place allowed to import `@prisma/client`, and `delete` only receives the id, not the tier). `UploadThingAdapter` uses `"<tier>:<key>"`; `R2Adapter` uses the bare R2 object key (single bucket, no ambiguity). `StubStorageAdapter` just needs *an* id and uses the provider key directly.

## Deployment

- **`prisma` (the CLI) moved from `devDependencies` to `dependencies`.** `docker-entrypoint.sh` runs `npx prisma migrate deploy` before starting the server, but the runtime Docker stage installs with `npm ci --omit=dev`; without this move the container would either fail offline or silently fetch the CLI from the network on every start.
- **`Dockerfile` copies `prisma/schema` (directory) and `prisma.config.ts`, not `prisma/schema.prisma`.** The schema was split into `prisma/schema/*.prisma` files before this session; the single-file `COPY` target hasn't existed since, so the image build was broken. Fixed to match `prisma.config.ts`'s `schema: 'prisma/schema'`.
- **`start:prod`/`start:worker` run `node dist/src/main`, not `node dist/main`** (as spec §1.1 literally lists). `nest build` compiles two top-level source roots (`src/` and `prisma/`) and preserves each one's path under `dist/`, so the entry point is `dist/src/main.js`; verified against the actual `npm run build` output, not assumed.

## Test infrastructure

- **`resetTestDatabase()` (destructive `TRUNCATE` + reseed) is called once from `test/global-setup.ts`, not from each e2e file's `beforeAll`.** Empirically, `vitest.config.ts`'s `fileParallelism: false` (nested inside the `e2e` project's `test` block) did not prevent two e2e files' `beforeAll` hooks from interleaving in-process against the one shared Postgres testcontainer — confirmed by reproducing a `TRUNCATE` from one file wiping a club row another file had just inserted. System data (roles/permissions/zones/points/settings/content) is seeded once, globally; each e2e file creates its own additively-named fixtures (clubs/users prefixed per file, e.g. `AU-CLUB-A`, `MX-CLUB-A`) so concurrent files never collide on unique keys. `resetTestDatabase()` and the advisory-lock guard around it are kept in `test/db.ts` for any future test that legitimately needs a full wipe.
- **A handful of Nest providers needed explicit `@Inject(Token)` instead of implicit constructor-type inference** (`EmailProviderPool`'s `EmailUsageRepository`/`ClockPort` params, `RbacRouteAudit`'s `ModulesContainer`/`Reflector` params) — under `unplugin-swc` (used by vitest) these resolved to `undefined` at runtime despite compiling and type-checking cleanly, while the exact same code booted fine under `tsx`. Root cause not fully isolated (suspected `emitDecoratorMetadata` interaction with swc's output for certain import shapes); the fix is mechanical and low-risk. If a provider throws `Nest can't resolve dependencies of X (?, ...)` for a class that's clearly registered, try adding an explicit `@Inject()` before assuming a real DI misconfiguration.
- **`RbacRouteAudit.findUndecoratedRoutes` guards `module.controllers?.values() ?? []`.** At least one module in the graph (observed with `@thallesp/nestjs-better-auth`'s dynamically registered module) produced a `Module` instance where `.controllers` was `undefined` rather than an empty `Map`, crashing the boot-time audit before it could report anything.
- **`RbacModule` imports `AuthModule`** so `PermissionGuard` can resolve `SessionContextPort` (provided and exported by `AuthModule`). Both modules are otherwise independent; `AuthModule` does not import `RbacModule`, so there's no cycle.

## Reporting (§3.6, §4.8, §5.2, §6.8)

- **`@RequirePermission` now accepts multiple keys (`@RequirePermission('a', 'b')` = "a OR b"), not just one.** Several routes in §5.2's table are gated by an explicit disjunction ("reports:submit own / reports:review s" for `GET/POST /reports`, "requests:manage; GET also reports:submit for open ones" for report requests). The existing decorator/guard only supported a single permission key. Extended `RequirePermission` to a rest-param array (backward compatible: existing single-arg call sites are unaffected) and `PermissionGuard` to pass if *any* listed permission is granted. Added `ScopeService.clubFilterAny`/`assertCanAccessClubAny` (union of `clubFilter`/`assertCanAccessClub` across the listed permissions) so services can compute the right scope regardless of which permission the caller actually holds.
- **`GET /reports` (and `GET /reports/:id`, `GET /report-schemas`) return 403, not 200-empty, for a caller holding neither `reports:submit` nor `reports:review`** (e.g. plain `member`, `project_admin`, `editing_team`). §4.8's own denial-matrix template row lists `member`/`project_admin` as "empty" and `editing_team` as `403` for the same missing-permission situation, which is internally inconsistent for a resource with no admitted broader read grant. Per §4.8 rule 8 ("when in doubt, restrict"), chose permission-gate-first (guard 403) uniformly over exposing a scope-only-filtered list to any authenticated user. `test/rbac/matrix.e2e.ts`'s reports section documents this explicitly.
- **`values.notes` (the schema's "Notes" section field, fieldKey `notes`) is excluded from `validateReportValues`/`collectClubIdsInValues` and is never read from or written to the `values` JSON blob.** `Report.notes` is already a first-class column (used by `PATCH /reports/:id {notes}` per the route table), and the web spec's "Notes for the district" textarea is one control, not two. The schema still seeds a `notes` field (per §6.8's literal field list, so the Form Builder can show/reorder/relabel it), but it's cosmetic metadata only — the validator special-cases and skips it by `fieldKey`.
- **`PATCH /reports/:id {status:'submitted'}` only accepts the transition from `draft` (or `queried`, so an officer can resubmit before a ZRR replies-in-reverse — not exercised in practice since the query-reply route already does the `queried -> submitted` transition explicitly). `values`/`notes` edits are only allowed while `status` is `draft` or `queried`** — restrictive reading of "submitting a report is `PATCH /reports/:id {status:'submitted'}`" (§5.1.1): once `submitted` or `scored`, the report is immutable via this route (a fresh query is the only way back to an editable state).
- **`ScopeService.clubFilter`/`ReportsRepository.whereFor` never merge the caller-supplied `filter[clubId]` with the scope directly — the service narrows scope first via `ScopeService.narrowClubs`, then the repository builds `WHERE clubId IN (narrowed scope)`, dropping the raw filter.** An earlier draft `OR`'d the scope where-clause with a raw `clubId: filter.clubId` fallback, which would have let any caller widen their own list query to an arbitrary club id by passing `filter[clubId]` — the exact scope-leak-through-filters problem §4.8 rule 3 warns about. Caught in review before it shipped; no scope-leak test failed because none existed yet, so `test/reports.e2e.ts`'s "ZRR sees only their zone" case is the regression guard for this specifically.
- **`ReportRequest.audience` is `{all?: boolean; clubIds?: string[]; zoneIds?: string[]}`**, not fully specified by the spec. A club is in-audience if `all`, or its id is in `clubIds`, or its `zoneId` is in `zoneIds`. `GET /report-requests` for a `reports:submit`-only caller returns every request whose audience currently matches their club (not filtered further by "already responded" — "open" is read as "applicable to me", the simpler and more restrictive of the two plausible readings, since narrowing further risks hiding a request the club still needs to act on).
- **The points engine (spec step 5) is explicitly out of scope here.** `src/points/adapters/point-source.port.ts` is a bare `PointSourceAdapter` interface stub with no implementation or module wiring — nothing in `src/reports/` or `src/points/` computes or persists `club_point_entries`. `src/points/adapters/report-field.derive.ts` implements and unit-tests the exact §6.8 derivation rules (`camps_organised`, `projects_initiated`, `vocational_workshops`, `flagship_continued`, `international_activities`, `max_collaborators`, plus the direct club-field and `filed_on_time` sources) as pure functions over a report's `values`/`filedOnTime`, ready for step 5 to call once it exists — but nothing currently calls `deriveReportPointSources` in the request path.
- **`AssistPort` mirrors `StoragePort`'s live/stub adapter-switch pattern exactly**: new env var `ASSIST_DRIVER` (`live|stub`, default `stub`, mirroring `STORAGE_DRIVER`), `AnthropicAssistAdapter` built against the real `@anthropic-ai/sdk` (already a dependency) using `env.ANTHROPIC_MODEL`/`env.ANTHROPIC_API_KEY`, `StubAssistAdapter` for tests/unconfigured envs. `GET /reports/:id/assist` is `reports:score`-gated per the route table; not exercised against a live Anthropic key in tests (`ASSIST_DRIVER` defaults to `stub`, matching the storage module's own untested-live-path precedent).
- **`report.submitted`/`report.queried` are plain in-process `@nestjs/event-emitter` events** (`EventEmitterModule.forRoot()` added to `AppModule`, first use of it in this codebase), payload shapes exported from `src/reports/report.events.ts`. Nothing subscribes yet — step 5 (points recompute) and step 9 (notifications/audit fan-out beyond what §4.6 already mandates inline) are the intended subscribers. Kept deliberately dependency-free (no queue, no BullMQ) since nothing consumes them yet and adding a queue for zero consumers would be unverifiable speculation.

## Caching and performance (§14)

- **`PrismaService`'s constructor returns `this.$extends(cacheInvalidationExtension)` cast back to `PrismaService`**, not `this`. Prisma's `$extends()` always returns a new proxied client rather than mutating the receiver, and every `*.repository.ts` in this repo already injects the concrete `PrismaService` class as its constructor param type, so changing that type across ~30 files was rejected as unnecessarily invasive. `onModuleInit`/`onModuleDestroy` (and a bespoke `onQuery` passthrough used only by test query-count assertions) are reattached onto the extended proxy via `Object.assign` in the constructor, since Nest calls lifecycle hooks by duck-typing (`typeof instance.onModuleInit === 'function'`), not `instanceof`. `class PrismaService extends PrismaClient<{log:[{emit:'event',level:'query'}]}>` (an explicit generic, not the bare `extends PrismaClient`) is required for `$on('query', ...)`/`onQuery` to type-check at all — Prisma's `$on` overload resolves its allowed event-name union from the class's own generic `log` config, which defaults to `never` when the subclass doesn't parameterise it.
- **The Prisma cache-invalidation extension (`src/prisma/cache-invalidation.extension.ts`) maps model → tags via `MODEL_TAG_MAP` (`src/cache/model-tag-map.ts`) and enqueues one purge per write**, covering `create|createMany|update|updateMany|upsert|delete|deleteMany` on every model through a single `$allOperations` hook (not one hook per model) so a newly added model needs no extension change, only a `MODEL_TAG_MAP` entry (enforced by `model-tag-map.spec.ts`'s exhaustiveness test, which statically scans a maintained list of public-facing `*.repository.ts` files for `this.prisma.<model>.` calls — this list must be kept in sync when a new public repository is added; `ProjectClub` is added by hand since it's read only via a nested Prisma `select`/relation, not a direct delegate call the regex can see).
- **`TAG_URL_MAP` (`src/cache/tag-url-map.ts`) lists only parameter-free public URLs** (`/public/clubs`, `/public/projects`, etc.), not slug-based detail routes (`/public/clubs/:slug`, `/public/projects/:slug`, `/public/events/:slug`, `/public/content/:pageKey`). Cloudflare purge-by-URL needs exact URLs and there is no bounded, enumerable set of slugs to purge ahead of time. L2 (Redis) invalidation for these detail routes is still fully correct and immediate — every distinct slug's cache key is a member of the same tag set as the list route, so `delByTag` deletes all of them — only the **edge** cache for a specific detail page can lag, bounded by `s-maxage` (600s), matching §14.4.3's own "never permanent" fallback language. The one exception is `/public/projects-summary/:key`, whose 5 keys are a small fixed enum (`PROJECT_KEYS`) and are enumerated concretely.
- **`CacheModule` registers `CachePurgeProcessor` (the BullMQ `cache.purge` worker) in both the API and worker processes**, not worker-only like the pre-existing `LinkHealthModule` pattern. Cache-invalidating writes happen inside API request handlers, so the API process is the natural place to also drain its own purge queue instead of depending on the worker always being reachable; both being able to consume is strictly more available, at the cost of needing `CLOUDFLARE_*` env vars on both Dokploy apps.
- **`NoopCloudflarePurgeClient` (bound whenever `CLOUDFLARE_API_EMAIL`/`_API_KEY`/`_ZONE_ID` are unset) records every call it skips** (`purgedUrlBatches`, `purgedPrefixes`), not just logs it. This doubles as the "fake Cloudflare client" the §14.7.2 e2e test needs to assert purge correctness — no separate test-only provider wiring was added, since local/test envs never set the Cloudflare vars and therefore always resolve to this class already.
- **`GET /public/live` (visitor count) and the ICS feeds (`/public/events/:slug.ics`, `/public/calendar.ics`) are deliberately excluded from `@CacheTags`/L2 caching.** `/public/live` exists specifically to stay live (5s edge TTL, polled every 10s by the frontend); putting it behind the 3600s L2 TTL would defeat its purpose. The ICS routes return `text/calendar`, not JSON, and the interceptor's L2 store round-trips values through `JSON.stringify`/`JSON.parse` — fine for a string body, but combined with Nest's `@Header('Content-Type', ...)` decorator ordering relative to interceptor short-circuiting, this was not verified and was judged not worth the risk for two low-traffic feed endpoints; they keep their pre-existing manual `setPublicCache(res, 300)` calls untouched.
- **Env additions (`CLOUDFLARE_API_EMAIL`, `CLOUDFLARE_API_KEY`, `CLOUDFLARE_ZONE_ID`, `CACHE_INVALIDATION`) are all optional/defaulted in `src/config/env.ts`**, not added to the production-required check in `parseEnv`. Omitting them degrades gracefully (edge purge skipped, logged) rather than blocking boot — matching `STORAGE_DRIVER=stub`'s existing precedent, and appropriate since Cloudflare purge is an optimisation, not a correctness requirement (L2/Postgres are still always correct).
- **`purgeAllStandalone()` (`src/cache/purge-all.standalone.ts`) is called from both `prisma/seed.ts` and `prisma/seed-system.ts`'s CLI entrypoint**, using its own short-lived, low-retry IORedis connection (`connectTimeout: 3000`, `maxRetriesPerRequest: 1`) rather than the app's long-lived `createCacheRedis()` config, and swallows all errors. `docker-entrypoint.sh` runs `seed-system.js` before the server starts with `set -e`; a Redis outage at deploy time must never block the container from booting, so this path can never throw.

## Site rebuild trigger (spec §14.9 follow-up)

- **`SITE_REBUILD_TAGS` excludes `zones` in addition to the spec's explicit `reports`/`points`/`members` list.** `Zone` only backs `GET /zones` (`@Authenticated()`-only, per the RBAC decision above) and the one place a public response mentions zone counts (`PublicHomeService`'s `home.stats`) reads a stored `Setting` value, not a live `Zone` query - so a `Zone` write never changes any `/public/*` payload. Per rule 8 (restrict when ambiguous), a tag with no public-facing effect stays off the rebuild allow-list; `site-rebuild-tags.spec.ts`'s exhaustiveness test enforces that every `CacheTag` is accounted for as either allow-listed or excluded, so a newly added tag can't silently land in neither.
- **The rebuild hook lives inside `CacheInvalidator.purge(tags)`** (calls `SiteRebuildTrigger.maybeEnqueue(tags)` after the existing L2/edge purge enqueue), not inside the Prisma extension itself or scattered across callers. `purge()` already gates on `CACHE_INVALIDATION=off` and is the one function every write-through-Prisma path reaches unconditionally (§14.4); `purgeAll()` (the seed/migration full-purge path) is deliberately left untouched, since seed runs already bypass `CacheInvalidator` entirely via `purgeAllStandalone()`'s own short-lived Redis connection.
- **Debounce is the fixed-`jobId` + `delay` BullMQ pattern**, not a Redis key with a TTL or a cron sweep: `addDelayedJob-6.lua` returns the existing job (via `handleDuplicatedJob`) when a job with that id already exists rather than erroring or resetting its delay, so repeated `queue.add()` calls during the window are no-ops and the job created by the first write in a burst is the only one that ever runs. `removeOnComplete: true` clears the key afterward so the next write starts a fresh window.
- **`GithubDispatchClient` and `SiteRebuildTrigger` each independently check `SITE_REBUILD_ENABLED`/token presence** rather than trusting the caller. This is deliberate belt-and-braces: a job already sitting in the delayed queue when `SITE_REBUILD_ENABLED` flips to `off` (or the token is pulled) must still no-op cleanly when it eventually runs, not throw.

## Members, directory, privacy, /me additions (spec step 6)

- **`MemberStatus` (locked schema, §3.3) has only `pending|approved|suspended` - there is no `rejected` value.** The task's wording ("approve/reject/suspend") is implemented as exactly two target statuses on `PATCH /members/:id`: `approved` and `suspended`. "Reject" a pending signup is the same wire call as "suspend" an approved member - `PATCH {status:'suspended', rejectionReason}` - since both mean "no active access" and the schema can't distinguish them by status alone; `rejectionReason` plus `approvedAt`/`approvedById` being null is what distinguishes "never approved" from "approved then revoked" if that's ever needed. Adding a `rejected` enum value would require a schema migration outside this task's scope (schema is explicitly "already in Prisma" per the brief) and risks colliding with concurrent schema work by other agents in this same repo.
- **Approving a member grants the club-scoped `member` role (`UserRole`); suspending revokes only that grant**, not any elevated role (`president`/`secretary`/`zrr`/`dsc`) the same user might separately hold. Managing elevated roles is `/roles` + `/user-roles` (`roles:manage`, super_admin only) - a different admin surface entirely. Per §4.8 rule 8 (restrict when ambiguous), member-status transitions were kept narrowly scoped to the one role they're actually responsible for; cascading a suspension to strip elevated roles too would be a bigger, un-asked-for behavior change to the RBAC surface. Re-approving after a suspension re-grants the same `member` role (idempotent upsert), so nothing needs manual repair.
- **A reason is required to decline a still-`pending` registration (`400` if `rejectionReason` is missing) but optional when suspending an already-`approved` member.** The mockup's roster-approval screen shows "Not ours" as the only decline action with no visible reason field in the compact card, but §5.2's route literally lists `rejectionReason` as part of the same PATCH body as `status`, and an audit trail with no reason for the *first* decision on a brand-new signup was judged the more useful data to force; a later suspend-for-cause on an existing member already has the member's history as context, so it isn't force-required there.
- **CSV roster import is stateless: no `ImportJob` (or similar) Prisma model exists**, and adding one for this task was judged out of scope (the locked schema doesn't have it, and a persisted, resumable import queue is a bigger feature than "preview then commit"). `POST /members/imports` returns a `crypto.randomUUID()` as `id` purely as a correlation token; nothing is stored server-side between preview and commit. `PATCH /members/imports/:id` therefore requires the caller to resubmit the (possibly hand-edited) `rows` array from the preview response - the `:id` param exists only to satisfy §5.1's resource-shaped URL convention, not because the server remembers anything by it. Re-checks dedup against the DB again at commit time (not just trusting the preview), so a stale preview never double-creates a member.
- **CSV import accepts `{ clubId, csv }` as a JSON body (`csv` = raw file text), not `multipart/form-data`.** Every other DTO in this API is a `nestjs-zod` JSON schema; introducing `multer`/`FileInterceptor` for exactly one endpoint was judged not worth the layering/testing cost when the frontend can just read the `File` via `FileReader.readAsText()` and post its contents as a string. If a later task needs true multipart (e.g. very large rosters), this can be revisited.
- **Imported rows (CSV commit) are created `approved` directly, bypassing `pending`**, mirroring the existing `migrate-legacy-users.ts` precedent and the mockup's own framing ("Two ways in, one dedup key" - self-signup waits for approval, a roster import is the officer already vouching for the list). Each gets a random unusable password (`hashPassword(randomBytes(24).toString('hex'))`) and a `password-reset-required` notification (existing `TemplateKey`), since they never chose a password themselves.
- **`GET /directory`'s privacy gate reads the *caller's* acceptance, not the *listed members'*.** `MemberPrivacyAcceptance(memberId, policyPublishedAt)` is checked against the current `ContentBlock('privacy-policy','body').publishedAt`; if the caller (who must already have `directory:view`) hasn't accepted the currently-published policy version, every request 409s with `PRIVACY_NOT_ACCEPTED` regardless of query filters - narrower than gating per-listed-member, and the only reading that makes "accept once, then browse" coherent. If the privacy-policy content block has never been published (`publishedAt` null), the directory is unconditionally 409 for everyone - no accepted-policy state can exist, so access is never granted by default (§4.8 rule 8).
- **Directory results never include email, phone, rotaryId, bio, qrToken, or scoring/points data** - the transformer (`directoryEntryDto`) is a hand-picked allow-list (id, fullName, photoUrl, skills, interests, club{id,name,shortName,zoneId,zoneName}), not the general `memberDto` with fields stripped. This makes "can't leak a new field by forgetting to strip it" the default for any future field added to `MemberProfile`.
- **`/me/card`'s `cardId` (e.g. `3011-DSE-0114`) is a cosmetic, non-authoritative display label**, not a stored or uniqueness-enforced identifier - computed at request time from the club's short name/name initials plus a stable hash of the member's own `id` (`buildCardId`, `src/me/member-card.util.ts`). The real security-relevant identifier for check-in scanning is `qrToken` (already a unique, DB-backed column); `cardId` exists purely so the membership-card UI has something that looks like the mockup's "ID 3011-DSE-0114" without inventing a new schema column or a sequence counter this task has no mandate to add.
- **`GET /me/qr.svg` encodes the raw `qrToken` string**, not a URL wrapping it. `POST /events/:id/checkins` (a later step, not built here) is specified to accept `{qrToken|memberId|walkInName+clubId}` directly, i.e. a scanner is expected to read the token value itself rather than parse a URL out of the QR payload.
- **`POST /members/register` is throttled 5/hour via a `MembersModule`-local `ThrottlerModule.forRoot(...)` instance**, independent of `PublicModule`'s own throttler registration - kept self-contained inside the module this task owns rather than depending on or modifying `PublicModule` (owned by a different, concurrently-active part of the build).
- **`GET /me/club` and `GET /me/card` delegate to the existing `ClubsService.get(access, clubId, {...})`** (via `MeModule` importing `ClubsModule`) rather than re-querying clubs directly from `MeRepository` - reuses the already-correct scope semantics (a member's own club is always in their `clubs:view` scope) instead of duplicating a second, parallel "is this really their club" check.
- **Badges, certificates, effort log, and the "MY CONTRIBUTION LOG" panel from the `/portal/me` mockup are explicitly out of scope for this task** - the task's own endpoint list has no certificates/badges/effort routes, and §5.2 places those under a later step. `/portal/me` (web) shows the membership card and QR only; `/portal/me/contributions` and `/portal/me/certificates` remain `ComingSoon`.
- **Push subscription registration (`POST /push-subscriptions`, `GET /push/vapid-key`) does not exist yet anywhere in this API** - no push module has been built by any task so far. The settings screen's "push-permission prompt" is implemented as the literal browser `Notification.requestPermission()` call and nothing else; wiring a real subscription to a backend is deferred until a push module exists.

## Content, settings, link-health, public-content admin (spec step 3)

- **`GET /settings` and `PATCH /settings` are gated by `settings:manage` alone, and the seeded `dsc` role does not hold that permission** (§4.4's DSC grant list stops at `public_content:manage`/`audit:view`; `settings:manage` is not listed there or for `zrr`). Only `super_admin` (which holds every permission) can manage district settings today. This reads as a real gap for day-to-day district operation, but per §4.8 rule 8 ("when in doubt, restrict") the seed was left as spec-literally written rather than silently widening a permission grant - `prisma/seed/roles.ts` is a shared file with heavy concurrent traffic from other tasks, and widening RBAC grants is explicitly called out as "a product decision for the district owner, never an implementer default." `test/content-settings-admin.e2e.ts` asserts this explicitly (dsc 403s on both routes; a locally-created `super_admin` session is used for the positive-path tests) so the gap is visible rather than silently masked.
- **`PATCH /content-blocks/:pageKey/:sectionKey` is gated by `content:edit` at the route level; the separate `content:publish` check happens inside `ContentService.editBlock`**, not as a second `@RequirePermission`, because the same route handles both "save a draft" and "publish" depending on whether the body includes `publish:true` - a caller with `content:edit` but not `content:publish` can still save drafts on the same endpoint. Verified with a locally-seeded custom role (`cs_content_editor_only`, `content:edit` only) in `test/content-settings-admin.e2e.ts`: draft save succeeds, publish attempt 403s.
- **Saving an `image`/`link` content block synchronously calls `LinkHealthService.checkAndTrack`**, which both returns the freshly-computed `linkStatus` in the PATCH response and upserts an `asset_links` row keyed on `(resourceType:'content_block', resourceId: '<pageKey>:<sectionKey>', url)` - this is what makes the row show up in `GET /asset-links` and get swept by the nightly recheck job without any separate registration step.
- **The public-content "reorder" capability is a bulk `POST /<resource>/reorder { ids: string[] }`** (order = array index) on all six orderable entities (achievements, partners, resources, past-drrs, district-team; publications/enquiries/sister-club-requests have no `order` column and no reorder route), rather than relying solely on §5.2's literal "PATCH accepts `order` for reordering." Both actually work (a single-row PATCH can still set `order` directly), but a bulk endpoint avoids N sequential PATCHes racing each other when a drag-and-drop UI reorders a whole list at once; recorded here since the task brief asked for a reorder endpoint explicitly and this is an addition beyond the literal route table, not a deviation from it.
- **`POST /sister-club-requests` accepts either `public_content:manage` (any club, any submittedById) or `clubs:edit` (own club only, enforced via `ScopeService.assertCanAccessClub`)** - the spec's route table says "sister-club POST by any president/secretary" without naming a permission key; `clubs:edit` is the permission both `president` and `secretary` already hold, scoped to their own club, so it was reused rather than inventing a new permission key.
- **`enquiries` and `sister-club-requests` admin routes use separate `createKeys`/`updateKeys` (API: distinct Zod schemas; web: `PublicContentTable`'s `createKeys`/`updateKeys` props) rather than one shared writable-field set** - both resources have a materially different shape for an admin-authored create (e.g. enquiries: `kind/name/email/message/routedTo`) versus an admin review-update (`status`/`assignedToId` only), and the API's `.strict()` Zod schemas reject any request carrying fields from the other shape.

## Mission 3011 and Drishti subdomains (spec step 12/13, salvaged from `.worktrees/mission3011-drishti`)

- **`PATCH /drishti/beneficiaries/:id` is gated by `subdomain:drishti:manage` alone - no OR-permission for the submitting president/secretary.** §5.2 only spells out the OR-permission (`subdomain:drishti:manage` OR own-club president/secretary) for `GET/POST`; PATCH's body (`stage`, `surgery`) is clinical progression data (moving a beneficiary to `operated`/`closed`, recording which hospital operated on them). Per rule 8 ("when in doubt, restrict"), a club officer who registers a beneficiary should not also be able to mark their own submission "operated" with no independent check - that would let an unverified claim of surgery completion feed the public 100-surgery gauge. Only the Drishti project admin (or super_admin) can transition `stage` or attach a `surgery`. - **`GET /mission3011/camps` stays `@Authenticated()` with no scope filter**, unlike `GET /clubs` (which this file's own earlier RBAC decision scope-filters by default per §5.1 rule 2). §5.2's literal table brackets this route `[auth]` with no permission key and no `s` marker, the only list route in the whole catalogue written that way, which reads as an intentional signal rather than an omission: camp records carry no PII (no beneficiary data, just venue/date/units/reviewer), the approved subset is already fully public via `GET /public/mission3011/dashboard`, and the whole point of the subdomain is a district-wide, semi-public leaderboard of blood-camp effort. Narrowing it to scope-filtered-by-club would hide a rejected/submitted camp's existence from every club except the submitter and the project admin, which contradicts the "camps directory" framing implied by the dashboard leaderboard. Recorded here as a deliberate exception rather than an oversight, since it visibly departs from the `GET /clubs` precedent.
- **`mission3011` and `drishti` were added to `SITE_REBUILD_TAGS`** (not excluded like `reports`/`points`/`members`/`zones`): both public dashboards (`/public/mission3011/dashboard`, `/public/drishti/dashboard`) are the kind of public marketing/impact page the static site prerenders, matching the existing `initiatives`/`settings` precedent (the five-project initiative cards already trigger a rebuild) rather than the portal-only precedent.

- **Drishti PII fails closed at two independent layers.** (1) `src/config/env.ts`'s `parseEnv` exits the process at boot in `NODE_ENV=production` if `DRISHTI_PII_KEY` is still the dev-default (`'de'.repeat(32)`), so a production deployment can never reach a beneficiary write/read without a real key. (2) `drishti-pii.util.ts`'s `keyBuffer()` independently throws `DRISHTI_PII_KEY missing or invalid` if the key is missing, empty, or not exactly 64 hex chars, regardless of environment - so a non-production caller (e.g. a future script, a differently-wired test) that somehow reaches `encryptPhone`/`decryptPhone` without a valid key gets a loud, immediate error instead of silently persisting or returning plaintext. Verified in `src/subdomains/drishti/drishti-pii.util.spec.ts`.

Fixed with a bounded poll (`waitUntilDashboardReflects`, 5s timeout) rather than removing the prior warm-up `GET`, since the warm-up is what makes the test actually exercise invalidation instead of a first-ever cache miss.
## RCL (Rotaract Champions League) subdomain (spec §7-9, §10, acceptance test #16)

- **"Current season" is read from the `rcl.season` setting, not `currentRyYear()`.** The task brief pointed at both a shared `ryYear` util (`src/common/ry-year.ts`) and a dedicated, already-seeded `rcl.season` setting (2026) and asked to "read [it] in your standings computation". A cricket league season doesn't necessarily track the July-June Rotary Year boundary the same way club reporting does, and the setting is independently overridable by district admins without a code change - the more specific, purpose-built lever wins. `RclSettingsRepository.get()` is the single place this is read (defaults `pointsWin:2, pointsTie:1, season:2026` if the rows are ever missing), used for: `POST /rcl/teams`'s default `season` when the body omits it, and `GET /public/rcl/standings`'s default `?season=`.
- **`RclFixture.season` is derived from its two teams, never accepted directly in `POST /rcl/fixtures`'s body.** Both teams must already share the same `season` (400 otherwise: "homeTeamId and awayTeamId must belong to the same season") - accepting an independent `season` field risked a fixture whose season disagreed with the teams it referenced, which `standings.ts` has no way to reconcile.
- **`POST /rcl/teams` for a non-manage-grant caller checks `ScopeService.canAccessClub(access, 'club_events:log', input.clubId)` directly against the body's `clubId`**, not the caller's own `MemberProfile.clubId` (unlike `mission3011`/`drishti`'s create methods, which infer the club from the caller's profile because their DTOs have no `clubId` field). RCL's spec explicitly puts `clubId` in the registration body, so the correct question is "does this caller's role scope cover this specific club", answered directly by the existing club-scope check - no `MeModule`/profile lookup needed, and `RclModule` doesn't import `MeModule` as a result.
- **A wrong-club `POST /rcl/teams` is 403, not 404.** Ground rule 4 (404 for out-of-scope reads/updates of an *existing* row, to prevent enumeration) doesn't apply to creating a brand-new row - there's nothing to enumerate. Mirrors `Mission3011CampsService.create`'s `ForbiddenException` precedent exactly. `PATCH /rcl/teams/:id` on an existing, out-of-scope team is still 404, matching drishti/mission3011's update precedent.
- **The one-team-per-`(season, clubId)` unique constraint is translated to `409 Conflict` at the repository boundary via a plain `RclTeamConflictError` (declared in `rcl.types.ts`, no `@prisma/client` import), not surfaced as a raw 500.** `RclTeamsRepository.create` is the only place that imports `Prisma`/catches `PrismaClientKnownRequestError` (`P2002`); the service layer only ever sees the domain-level error, keeping "`*.repository.ts` is the only file allowed to import `@prisma/client`" intact.
- **`GET /rcl/teams` (and `GET /rcl/teams/:id`) are club-scoped for a `club_events:log`-only caller** (own club(s) via `ScopeService.clubFilter`/`assertCanAccessClub`; `subdomain:rcl:manage` sees every club), mirroring drishti's corrected (post-mortem) behaviour rather than mission3011 camps' deliberately-open list. `captainPhone` is real contact PII for an officer who isn't necessarily the district admin, and unlike mission3011's approved-camp leaderboard, nothing about team registration needs to be readable district-wide pre-publication - the public standings/fixtures endpoints never expose captain contact details at all, only team names.
- **`GET /rcl/fixtures` (the authed list) is deliberately *not* club-scoped**, matching `GET /mission3011/camps`'s documented exception rather than the teams precedent above: fixture rows carry no PII (two team names, a venue, a scheduled time, and score data once entered), and the identical data is already fully public via `GET /public/rcl/fixtures` - narrowing the authed list would just make an officer's own in-app schedule view worse than the public one for no scoping benefit.
- **`PUT /rcl/fixtures/:id` accepts a nested `result: {...}` object (all score fields together) alongside a top-level, independent `status`/`scheduledAt`/`venue`**, rather than flat score fields at the top level. This lets one route cleanly express three different admin actions - reschedule only, mark abandoned with no score at all, or enter a full result - without a combinatorial flat-field mess. Setting `result` flips `status` to `completed` automatically *unless* the same request's `status` is explicitly `abandoned` (a match can be curtailed by weather but still have a partial score worth recording for NRR).
- **An `abandoned` fixture with no `RclResult` row at all still awards `pointsTie` to both teams but contributes zero runs/overs to NRR** (`standings.ts` treats a fixture with `result: null` as `winnerTeamId: null` for points purposes, and simply skips the runs/overs accumulation). This is the "rained out before a ball was bowled" case; an abandoned match that *did* get partway through (a real `RclResult` row with partial overs) contributes its actual runs/overs like any other result - `standings.spec.ts` covers both shapes.
- **`RclTeam.status = 'withdrawn'` teams are excluded from the standings team pool and from fixture-generation eligibility** (`RclStandingsRepository.teamsForSeason` filters `status: { not: 'withdrawn' } }`), but are still fully visible/editable via the authed `GET/PATCH /rcl/teams` routes. A withdrawn team isn't competing, so it has no place in a table sorted by win/loss record; it still needs to exist as a record for the club's own registration history.
- **`'rcl'` was added to `CACHE_TAGS`/`MODEL_TAG_MAP` (`RclTeam|RclPlayer|RclFixture|RclResult`)/`TAG_URL_MAP` (`/public/rcl/standings`, `/public/rcl/fixtures`) and to `SITE_REBUILD_TAGS`**, following the `mission3011`/`drishti` precedent exactly (both are public, prerendered-by-the-static-site pages, not portal-only data) rather than the excluded `reports`/`points`/`members`/`zones` list.
- **Audit records are written for team status transitions (`rcl.team.status_changed`) and fixture result entry (`rcl.fixture.result_entered`)**, even though neither is in §4.6's literal mandatory-audit list (which predates this subdomain). Both are exactly the shape of action §4.6 already covers for sibling subdomains (camp approve/reject, beneficiary stage change) - a district-visible status change with real downstream effect (public standings) - so the same bar was applied by analogy rather than skipped for being technically unlisted.
- **No `GET /rcl/fixtures/:id` or notification-on-registration routes were added.** The task's literal endpoint list (§10's exact bullet) has no single-fixture-by-id route and no mention of notifying anyone on team registration/result entry (unlike mission3011/drishti's `NotificationPort.notify` calls on submit/approve) - adding either would be scope creep beyond what was asked, and there's no district-admin-facing "camp submitted, please review" queue for RCL the way there is for mission3011 camps (fixture creation and result entry are both admin-initiated already, so there's no pending state for anyone to be notified about).

- **Post-merge fix: `GET /drishti/beneficiaries` and `GET /drishti/beneficiaries/:id` were shipped with only `@Authenticated()`, no club scoping** - the salvaged code correctly gated `POST` (`club_events:log` OR `subdomain:drishti:manage`) but the two read routes let ANY authenticated user (any club's plain `member`, with no officer or manage grant at all) list or fetch every beneficiary's name/age/gender/eye/campLocation/notes across every club - only `phone` was permission-masked. This is a real PII leak, caught by a second reviewing agent building the frontend against the real controller source, not by the original e2e suite (which only asserted phone-masking, never cross-club or neither-permission denial on the read routes). Fixed to exactly mirror this repo's own established `reports.controller.ts` precedent: both routes now require `@RequirePermission('club_events:log', 'subdomain:drishti:manage')` (403 for a caller holding neither, matching the "GET /reports 403 not empty" convention above), and the service computes a club scope - `{all:true}` for a manage-grant caller, `ScopeService.clubFilter(access, 'club_events:log')` (own club(s) only) otherwise - narrowed by any requested `filter[clubId]` and passed into the repository's pre-existing (but previously never invoked) `whereFor(filter, scope)` clause. `GET /drishti/beneficiaries/:id` for an out-of-scope existing row now 404s (ground rule 4: never 403, to avoid confirming a specific beneficiary id exists to a caller who can't see it). New e2e coverage: `test/drishti.e2e.ts` gained a second club/president (`DR-CLUB-B`) and two tests - a plain member gets 403 on both list and get; a president of club B cannot see club A's beneficiaries in their list and gets 404 reading one by id directly, while the drishti admin still sees it. This is exactly the class of bug §4.8 rule 1 ("an e2e test that an in-scope caller succeeds AND an out-of-scope caller gets 404/403... a route without all three is not mergeable") exists to catch, and it slipped through the first pass - recorded here as a reminder that "phone is masked" is not the same test as "the record is scoped."

## Career Bridge subdomain (spec §10 step 13)

- **The task brief that kicked this off described a simplified single-step "post → admin approve/reject" flow, but the real spec and locked schema require an email-verification step first.** `CbListing.verifyToken` (unique, nullable) exists in the locked schema, §12 acceptance test 15 literally states "post → `pending_email`; verify token → `pending`; verify by admin → visible", and `NotificationPort`'s `TemplateKey` union already carries both `listing-verify` and `listing-verified`. The spec is the authoritative source over a paraphrased task description, so the full three-stage flow (`pending_email` → poster clicks emailed link → `pending` → admin verifies → `verified`) was implemented, not the simplified version.
- **No template/notification exists for "admin needs to review a new pending listing" or "your listing was rejected".** `TemplateKey` only defines `listing-verify` (sent to the poster to confirm their own email) and `listing-verified` (sent to the poster once an admin approves). Unlike Mission 3011/Drishti's `camp-submitted`/`camp-approved` pair, Career Bridge's admins are expected to pull from the verification desk rather than be pushed a notification, and a reject is silent by design - adding new `TemplateKey` values for this was judged an unrequested scope increase, not a missing piece blocking a real requirement.
- **The public submission form's honeypot field is named `website`, accepted permissively by the DTO, and handled in the service layer, not the validation layer.** A filled honeypot returns the exact same `{id, status:'pending_email'}` shape as a real accepted submission (with a random, never-persisted `id`) so a scripted bot cannot distinguish "silently dropped" from "accepted" and has no signal to adapt against. Rejecting with a 400 at the Zod layer was deliberately avoided for the same reason.
- **`mode` (remote/onsite/hybrid) is a plain `String` column in the locked schema but constrained to an enum at the DTO layer.** The UI needs a fixed set of choices; storing free text in the column while validating the enum in Zod avoids a schema change for what the UI will only ever offer as a picker.
- **No per-surface web origin env var exists** (§11.2's env list has no `CAREERBRIDGE_WEB_ORIGIN` or equivalent for any subdomain), so the verify-email link is built from `WEB_ORIGINS` by finding the entry containing `"careerbridge"` and falling back to the first configured origin with `?surface=careerbridge` appended - this also makes the link work against `resolveSurface`'s `?surface=` local-dev fallback (`rac3011-web/src/app/host.ts`) without a new env var.
- **The nightly expiry job is a BullMQ queue (`careerbridge-expiry`) + scheduler + `WorkerHost` processor**, mirroring `LinkHealthModule`'s existing scheduler pattern exactly rather than introducing `@nestjs/schedule` as a second scheduling mechanism. `CareerbridgeModule` calls `BullModule.registerQueue(...)` only (no second `forRoot`) and relies on the global BullMQ config already registered by `LinkHealthModule` (loaded earlier in `httpModules` via `LinkHealthAdminModule`) - two competing `forRoot()` calls would double-register the same global config token.
- **Public browse/detail filter on both `status IN (verified, filled)` AND `expiresAt` in the future**, not status alone - defense in depth against the nightly job not having run yet for a listing whose `expiresAt` just passed. The nightly job (`careerbridge-expiry` queue, 03:00 IST) then flips `status` to `expired` for anything already past `expiresAt`, keeping the public read-path correct even between runs.
- **`careerbridge.expiryDays` defaults to 60 when unset in `Setting`**, chosen as a reasonable shelf-life default for a job/internship/mentorship posting; the seed explicitly sets it to 60 too so the admin settings screen shows a real value rather than relying on the code fallback silently.
- **The public detail page's "reveal contact" affordance is a frontend-only UI gate, not a server-side access control.** `contactEmail`/`applyUrl` are already present in the `GET /public/careerbridge/listings/:id` response for any caller - a listing's contact info is meant to be given out to interested applicants, unlike Drishti's beneficiary PII. The "click to reveal" pattern only slows casual scraping; it isn't a security boundary and isn't tested as one.
- **`verifyToken` is set back to `null` once consumed** (`markPending`), both because it's no longer needed and so replaying the same emailed link twice 400s ("Invalid or already-used verification token") instead of silently re-processing.
- **`CbListing` has no club/officer relation at all** (posts come from "any club, company, or individual" per spec), so `CareerbridgeListingsService` has no `ScopeService`/club-scoping logic anywhere - the only gate on admin routes is the flat `subdomain:careerbridge:manage` permission check, matching Drishti's `hasManageGrant` pattern for its manage-only routes.

- **Support-club registration is a single `POST /ride/support-clubs` that upserts on `(ryYear, clubId)`, not a separate PATCH.** The spec's API list only names `GET/POST /ride/support-clubs` (no PATCH), matching "one per club per RY; editable" - re-submitting the form just updates the existing row in place. `ryYear` is server-derived from `currentRyYear()` for officer callers (not client-supplied) since letting a club pick an arbitrary RY for their own registration has no legitimate use case and only invites mistakes; a manage-grant caller can still pass an explicit `clubId`/`ryYear` to backfill another club or a past year, mirroring Drishti's `create()` allowing manage callers to target a `clubId` the officer path can't.
- **`RideDelegation` CRUD (create/update/status) is entirely `subdomain:ride:manage`-gated, with no club-officer submission path at all** - unlike Mission3011/Drishti's "officer submits, admin reviews" flow, the spec's route table puts delegation CRUD solely under "`/admin` (`subdomain:ride:manage`)". A delegation record represents an inbound visit the district itself is coordinating, not something an individual club proposes, so there's no analogous "officer-owns-their-submission" scope to add. Status transitions (`planned/confirmed/completed/cancelled`) are unconstrained (no forward-only ordering check like Drishti's stage progression), since the spec describes plain CRUD here, not a reviewed pipeline.
- **Public `/incoming` excludes `cancelled` delegations** (`RideDelegationsRepository.findIncoming()` filters `status: {not: 'cancelled'}`) - a visit that fell through has no reason to keep advertising a host-family need to the public; the admin panel remains the source of truth for cancelled records via the full manage-gated list.
- **`PUT /ride/delegations/:id/hosts` fully replaces the host set** (delete-then-recreate in one transaction) rather than diff-patching individual rows, matching the spec's literal wording ("replaces set"). The repository returns the union of previously- and newly-assigned club ids so the service can call `PointsEngineService.recompute({clubId, ryYear, trigger})` for every affected club, not just the newly-added ones - this is what makes a reassignment (`A -> B`) correctly zero out A's RIDE-derived points rather than leaving stale entries, verified in `test/ride.e2e.ts` by asserting A's `international_services` category total drops after reassignment.
- **Added a real `RideHostingAdapter` (`src/points/adapters/ride-hosting.adapter.ts`) for the `ride_hosting` point-source type, replacing its `DeferredSourceAdapter` placeholder** now that `RideDelegationHost` rows actually exist. Handles `sourceKey` `days_hosted` and `members_sent` (per-unit, summed across a club's host rows for the RY) and `hosted_and_sent` (flat bonus when both are nonzero) - these three exactly reproduce spec §12 acceptance test 14's numbers (3 days/40pts + 2 members/30pts + 50pt flat bonus = 120/60/50). **`ride_hosting:days_visited` is deliberately left unhandled** (falls through to `default: return null`, same zero-input behavior `DeferredSourceAdapter` gave it before): that sourceKey is for RID members *travelling out* to another district, and neither the schema (`RideDelegationHost` has no "visiting" concept) nor this task's brief ("inbound delegation hosting") covers outbound tracking - building a real adapter for it now would mean inventing data that doesn't exist yet.
- **`points-source.repository.ts` gained `findRideHostingTotals(clubId, ryYear)`** (a single `rideDelegationHost.aggregate` summing `daysHosted`/`membersSent` for the club across all its delegations in that RY), following the exact same shape as the adjacent `findClubFacts`/`countApprovedMembers` methods - this repository is the only place any points adapter is allowed to reach Prisma directly.
- **Registered `'ride'` in the three cache-tag support files that don't auto-generate from `PROJECT_KEYS`**: `TAG_URL_MAP` (`src/cache/tag-url-map.ts`, purge targets for `/public/ride/incoming`, `/public/ride/gallery`, `/public/ride/dashboard`), `SITE_REBUILD_TAGS` (`src/site-rebuild/site-rebuild-tags.ts` - RIDE's public pages are prerendered like Mission3011/Drishti's dashboards), and `MODEL_TAG_MAP` (`src/cache/model-tag-map.ts`, all four `Ride*` models -> `['ride']`). All three have their own exhaustiveness unit tests that fail loudly if a `CacheTag` is left unaccounted for, which is how the initial omission was caught before push.
- **Gallery `kind` is validated as a `'photo'|'video'` enum at the DTO layer but stays a bare `String` column at the repository boundary** (schema comment: `/* photo|video */`, not a real Prisma enum) - the repository narrows the Prisma-returned `string` to `GalleryItemKind` via an explicit `toRow()` mapper, the one place allowed to know the column isn't really enum-typed.
- **No new upload primitive was built for gallery photos.** Following the same convention already established by Mission3011's `photos: string[]` field, `RideGalleryItem.url` just stores whatever URL the client sends - the existing `FileUpload` web component (grant → direct-to-provider upload → finalise) already produces a plain URL string for the "Upload" path and accepts a pasted link for the "paste a link" path (`AssetUrlField`/`FileUploadValue`), so the API side needs nothing beyond validating the resulting string is a well-formed URL.

## Notifications dispatch (spec §7, step 9)

- **`ConsoleNotificationAdapter` is kept as a recorder, not replaced.** `NotificationDispatchService` (the new `NotificationPort` implementation) always calls `ConsoleNotificationAdapter.notify(input)` after handling a request, purely so its `sent` ring buffer and `lastFor()` keep working for existing e2e tests (`test/auth-flow.ts`, `test/careerbridge.e2e.ts`, `test/feedback.e2e.ts`, `test/ride.e2e.ts` all read OTPs/links off it). The console log line itself is now a side channel, not the delivery mechanism.
- **The `push` channel is fully deferred, not partially stubbed.** `NotificationDispatchService.notify` only ever creates outbox rows and enqueues jobs for the `email` channel; a request naming `push` (alone or alongside `email`) is silently accepted with no row, no job, and no error for the push part. Building a push outbox/worker now would be speculative, since no caller in this codebase requests push yet.
- **Enqueue failures do not fail the request; a sweeper repairs them.** If `queue.add()` throws (e.g. Redis is briefly unavailable) after the outbox row was already committed, `NotificationDispatchService` logs at error level and returns normally, leaving the row `queued`. `NotificationSweepScheduler` registers a repeatable BullMQ job (`upsertJobScheduler`, job name `sweep`, every 5 minutes, same pattern as `CareerbridgeExpiryScheduler`) on the same `notifications` queue; `NotificationSendProcessor.process` branches on `job.name` and, for `sweep`, re-enqueues a `send` job for every `queued` row older than 2 minutes with `attempts < NOTIFICATIONS_MAX_ATTEMPTS` (200 per run). Database failures from the outbox repository are never swallowed and propagate out of `notify()`.
- **`FakeEmailTransport` replaces all four real transports in `NODE_ENV=test`**, not just in unit tests. `emailTransportsProvider`'s factory (`email-provider-pool.service.ts`) checks `env.NODE_ENV === 'test'` and returns `[fake]` instead of `[oracle, resend, mailgun, gmail]`, mirroring the `cloudflareConfigured ? Live : Noop` env-conditional pattern already used in `cache.module.ts`. This lets e2e tests assert real send/failure behaviour (`FakeEmailTransport.failNext`) without ever touching a real SMTP/API provider, and without a separate test-only module.
- **Retry policy is fixed, not tunable per template.** Every `send` job (both the original enqueue and the sweeper's re-enqueue) uses the same options: `attempts: 5`, `backoff: { type: 'exponential', delay: NOTIFICATIONS_RETRY_DELAY_MS }` (new env var, default 30000ms), `removeOnComplete: true`, `removeOnFail: 1000`. `job.attemptsMade + 1 >= (job.opts.attempts ?? 1)` decides whether a failed attempt is final (`NotificationOutbox.status -> failed`) or leaves the row `queued` for BullMQ's own retry.
- **Templates beyond `otp`/`password-reset-required` are a generic fallback by design, enforced at compile time.** `templates/index.ts`'s `TEMPLATES: Record<TemplateKey, NotificationTemplate>` maps every other `TemplateKey` to `genericTemplate(key)` (HTML-escaped key/value dump); if a future `TemplateKey` is added to `notification.port.ts` without a matching entry here, the file fails to compile rather than silently falling through at runtime.
- **Under full e2e-suite load, `test/notifications.e2e.ts` can occasionally fail in the same way `test/cache.e2e.ts` already does (§14 test infrastructure note above), for the same reason.** Every e2e file spins up its own `createTestApp()`, including its own `NotificationSendProcessor` BullMQ worker bound to the same `notifications` queue name on the one shared Redis instance for the whole suite run; if a previous file's app hasn't fully torn down its worker before the next file's app starts, both workers can compete for the same queue and a job can be picked up by a different file's worker instance (which has its own, separate `FakeEmailTransport`). The database side effects (`NotificationOutbox.status/provider/sentAt`) are always correct regardless of which file's worker processed the job, but an in-memory assertion against *this* file's `FakeEmailTransport.sent` can occasionally miss the message. Verified reliable (isolated `npx vitest run --project e2e test/notifications.e2e.ts`, repeated) at 100%; not reliable under `npm run test:e2e` on a heavily loaded shared machine, matching the pre-existing BullMQ "Missing key for job" errors already visible on unrelated queues (`careerbridge-expiry`, `rcl`, `storage`) under the same conditions. No code change was made to work around this: it is a test-harness limitation (one Redis, many independently-booted app instances, same queue names), not a defect in the dispatch/worker implementation.
